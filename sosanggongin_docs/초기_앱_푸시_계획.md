# 소상공인 플랫폼 푸시 알림 시스템 (초기 운영 모델)

## 1. 문서 목적

본 문서는 **초기 서비스 단계(사용자 약 100명 규모)**에서 적용할 푸시 알림 시스템의 실제 구현 방식을 정의한다.

기존 설계 문서는 **확장 가능한 아키텍처를 기준으로 작성**되었으나, 초기 단계에서는 모든 구성요소를 구현하는 것이 **개발 비용 대비 효율적이지 않다**.

따라서 본 문서는 다음을 목표로 한다.

* 초기 서비스에 **적합한 최소 구현 구조(MVP)** 정의
* 불필요한 인프라 구축 방지
* 향후 확장 가능한 구조 유지
* 개발 범위 명확화

---

# 2. 현재 서비스 규모 기준

현재 서비스 목표

| 항목        | 값          |
| --------- | ---------- |
| 예상 사용자    | 약 100명     |
| 푸시 발생 빈도  | 낮음 (공지 중심) |
| 동시 푸시 트래픽 | 매우 낮음      |

이 규모에서는 다음과 같은 특징이 있다.

* 푸시 전송량이 적음
* 서버 부하 발생 가능성 낮음
* 복잡한 메시지 처리 시스템 불필요

따라서 **단순 구조로 구현하는 것이 가장 합리적이다.**

---

# 3. 초기 푸시 시스템 아키텍처

초기 시스템은 다음 구조를 사용한다.

```
Admin 공지 생성
      ↓
Spring Server
      ↓
Notification DB 저장
      ↓
Device Token 조회
      ↓
Firebase Cloud Messaging 전송
      ↓
사용자 디바이스 수신
```

특징

* Push Queue 없음
* Worker 없음
* Topic Push 미사용

즉, **서버에서 직접 Push를 발송하는 단순 구조**이다.

---

# 4. 초기 시스템 구성 요소

초기 시스템은 다음 4가지 구성요소로 구성된다.

## 4.1 Notification 시스템

푸시는 전달 실패 가능성이 있으므로, **알림 데이터는 서버 DB에 저장한다.**

### Notification Table

| 컬럼         | 설명     |
| ---------- | ------ |
| id         | 알림 ID  |
| user_id    | 사용자 ID |
| type       | 알림 유형  |
| title      | 제목     |
| message    | 메시지    |
| data_json  | 추가 데이터 |
| read       | 읽음 여부  |
| created_at | 생성 시각  |

### 역할

* 알림 이력 관리
* 앱 알림센터 데이터 제공
* Push 실패 상황 대응

---

## 4.2 Device Token 관리

푸시는 디바이스 단위로 전송되므로 **Device Token 관리가 필요하다.**

### Device Table

| 컬럼           | 설명            |
| ------------ | ------------- |
| id           | 디바이스 ID       |
| user_id      | 사용자 ID        |
| device_token | FCM 토큰        |
| device_os    | Android / iOS |
| created_at   | 등록 시각         |

### 처리 방식

로그인 시 Flutter 앱에서 FCM Token을 서버로 전송한다.

```
Flutter
   ↓
POST /devices
   ↓
Spring Server
   ↓
Device DB 저장
```

---

## 4.3 Push 발송 방식

초기 시스템에서는 **Direct Push 방식**을 사용한다.

```
Server
   ↓
FCM API 호출
   ↓
User Device
```

### 특징

* 단순 구현
* 빠른 개발 가능
* 초기 서비스에 충분한 성능

---

## 4.4 알림 조회 API

앱에서는 서버 기준으로 알림 목록을 조회한다.

### 알림 목록

```
GET /notifications
```

### 읽음 처리

```
PATCH /notifications/{id}/read
```

# 5. 초기 단계에서 제외되는 시스템

다음 시스템은 **초기 단계에서는 구현하지 않는다.**

## 5.1 Push Queue

### 개념

푸시 요청을 메시지 큐에 적재하여 비동기로 처리하는 구조

예

```
Server
  ↓
Queue
  ↓
Push Worker
  ↓
Push Provider
```

### 제외 이유

* 현재 푸시 트래픽 매우 낮음
* 서버 직접 호출로 충분
* 인프라 복잡도 증가

### 도입 시점

다음 조건 발생 시 도입

* 사용자 10,000명 이상
* 대량 푸시 이벤트 발생
* 푸시 처리 병목 발생

---

## 5.2 Push Worker

### 개념

Queue에 적재된 푸시 작업을 처리하는 Worker 서버

### 제외 이유

* Queue 미사용
* 단일 서버로 충분

---

## 5.3 Retry 시스템

### 개념

푸시 실패 시 재시도 처리

### 제외 이유

* 초기 푸시는 중요도가 낮음
* Notification DB가 이미 백업 역할 수행

앱은 서버 알림 목록을 조회하므로 **Push 실패는 치명적 문제가 아니다.**

---

## 5.4 Topic Push

### 개념

FCM Topic 기반 대량 푸시

예

```
/topic/all_users
```

### 제외 이유

* 초기 사용자 수 적음
* Device Token 조회 비용 낮음

---

# 6. 초기 시스템의 장점

이 구조는 다음 장점을 가진다.

### 개발 속도

복잡한 인프라 없이 빠르게 구현 가능

### 유지보수 단순성

구조가 단순하여 디버깅이 쉽다.

### 확장 가능성

초기 구조는 다음 구조로 확장 가능하다.

```
현재
Server → FCM

확장
Server → Queue → Worker → FCM
```

---

# 7. 향후 확장 전략

서비스 성장 시 다음 단계를 적용한다.

### 사용자 1,000+

* Topic Push 도입

### 사용자 10,000+

* Push Queue 도입
* Worker 서버 분리

### 사용자 100,000+

* Push Retry 시스템
* Push 로그 분석
* Rate Limit 관리

---

# 8. 결론

초기 서비스 단계에서는 **단순한 Direct Push 구조**가 가장 효율적이다.

핵심 원칙

1. Notification은 반드시 서버 DB에 저장
2. Push는 단순 전달 수단
3. 초기에는 복잡한 인프라 도입하지 않음
4. 서비스 성장에 따라 단계적으로 확장

이 접근 방식은 **개발 속도와 확장성을 동시에 확보하는 전략**이다.
