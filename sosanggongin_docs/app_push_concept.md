# 소상공인 플랫폼 푸시 알림 시스템 설계

## 1. 개요

본 문서는 소상공인 플랫폼에서 사장님에게 공지사항 및 서비스 알림을 전달하기 위한 푸시 알림 시스템 설계를 정의합니다.

### 시스템 목표

푸시 알림 시스템은 단순 메시지 전달 기능을 넘어 다음 목표를 가집니다.

- **사용자에게 실시간 이벤트 전달**
- **서비스 공지 및 운영 알림 전달**
- **서비스 확장 시에도 대응 가능한 확장성 있는 구조**

### 설계 철학

푸시는 모바일 OS 환경 및 네트워크 상황에 따라 전달이 보장되지 않는 특성을 가지므로, 본 시스템은 **푸시 자체가 아닌 서버 기반 알림 시스템(Notification System)**을 중심으로 설계합니다.

푸시 알림은 해당 알림 시스템을 사용자에게 전달하기 위한 **트리거 역할**을 수행합니다.

---

## 2. 푸시 알림 시스템 전체 구조

### 시스템 플로우

```
Event 발생
    ↓
Notification 생성
    ↓
Notification DB 저장
    ↓
Push 메시지 생성
    ↓
Push Queue 적재
    ↓
Push Worker 처리
    ↓
Push Provider 전송
    ↓
사용자 디바이스 수신
    ↓
앱 실행 및 Deep Link 이동
```

### 지원하는 Push Provider

- **Firebase Cloud Messaging (FCM)**
- **Apple Push Notification Service (APNs)**

### 구조 채택 근거

- 푸시 전달 실패 상황 대응
- 대규모 푸시 트래픽 처리
- 알림 이력 관리

---

## 3. Push와 Notification 시스템 분리

푸시 시스템 설계에서 가장 중요한 원칙은 다음입니다.

> **Push ≠ Notification**

푸시는 알림 전달 수단이며 실제 알림 데이터는 서버에 저장되어야 합니다.

### 설계 구조

```
Event 발생
    ↓
Notification DB 저장
    ↓
Push 발송
```

### 설계 근거

모바일 푸시는 다음 이유로 전달 보장이 없습니다.

- 네트워크 불안정
- OS 절전 정책
- 사용자 알림 차단
- Push Provider 제한

따라서 **알림 데이터는 반드시 서버 DB에 저장되어야** 하며, 앱은 항상 서버 기준으로 알림을 조회합니다.

---

## 4. Notification 데이터 모델

알림은 서버 DB에서 관리됩니다.

### Notification Table 구조

| 컬럼명 | 설명 |
|--------|------|
| id | 알림 ID |
| user_id | 사용자 ID |
| type | 알림 유형 |
| title | 제목 |
| message | 메시지 |
| read | 읽음 여부 |
| created_at | 생성 일시 |

### 예시 데이터

```
id: 101
user_id: 42
type: announcement
title: 새 공지사항 발생
message: 새로운 공지사항이 발생했습니다
read: false
created_at: 2024-03-11 14:30:00
```

### 알림 조회

앱 실행 시 다음과 같이 알림 목록을 조회합니다.

```sql
SELECT *
FROM notification
WHERE user_id = ?
ORDER BY created_at DESC
```

## 5. 사용자 디바이스 식별

푸시를 전송하기 위해 사용자 디바이스를 식별해야 합니다.

### Device 정보 구조

| 컬럼명 | 설명 |
|--------|------|
| id | 디바이스 ID |
| user_id | 사용자 ID |
| device_token | FCM/APNs 토큰 |
| device_os | 디바이스 OS (iOS/Android) |
| created_at | 등록 일시 |

### 핵심 식별 정보

- **user_id**: 사용자를 식별하는 고유값
- **device_token**: FCM 또는 APNs에서 발급한 고유 토큰

### 설계 이유

푸시는 디바이스 단위로 전송되므로 사용자와 디바이스 매핑 관계를 유지해야 합니다.

또한 다음 상황을 고려합니다:

- 사용자가 여러 디바이스 사용
- 디바이스 변경
- 앱 재설치

로그인 시 최신 device_token을 서버에 갱신하도록 합니다.

## 6. Push 대상 선정 전략

푸시 대상 선정 방식은 크게 두 가지 방식이 있습니다.

### Device Token Push

**device_token 기반 전송**

- **특징**:
  - 특정 사용자 대상 푸시
  - 개별 권한 제어 가능
- **사용 예**:
  - 공지사항 알림
  - 결제 알림
  - 리뷰 알림

### Topic Push

**topic 기반 전송**

- **특징**:
  - 대규모 사용자 대상 푸시
  - DB 조회 없이 전송 가능
- **사용 예**:
  - 전체 공지
  - 업종 공지
  - 지역 공지

---

## 7. Push 대상 선정 전략 (Hybrid 방식)

서비스 확장성을 고려하여 **Hybrid 방식**을 채택합니다.

### 전략

- **공지 알림** → Topic Push
- **개별 알림** → Device Token Push

### 예시

| 알림 유형 | 방식 |
|---------|------|
| 전체 공지 | topic |
| 업종 공지 | topic |
| 지역 공지 | topic |
| 공지사항 알림 | device_token |
| 리뷰 알림 | device_token |

이 방식은 대규모 트래픽 처리와 사용자 맞춤 알림을 동시에 해결할 수 있습니다.

---

## 8. Push Queue 설계

대규모 푸시 전송 시 서버 부하를 방지하기 위해 **Queue 기반 구조**를 사용합니다.

### 시스템 구조

```
Server
    ↓
Message Queue
    ↓
Push Worker
    ↓
Push Provider
```

### 설계 이유

#### 1. 트래픽 완충

대량 푸시 요청이 발생할 경우 트래픽을 흡수합니다.

#### 2. 비동기 처리

서버는 푸시 전송 완료를 기다리지 않고 다음 작업을 수행할 수 있습니다.

#### 3. 장애 복구

푸시 실패 시 재시도를 수행할 수 있습니다.

---

## 9. Push Payload 설계

푸시는 단순 메시지가 아니라 이동 정보를 포함한 Payload를 전달합니다.

### Push Payload 예시

```json
{
  "notification": {
    "title": "새 공지사항",
    "body": "새로운 공지사항이 발생했습니다"
  },
  "data": {
    "type": "announcement",
    "announcementId": "123",
    "storeId": "10"
  }
}
```

**data 영역**을 활용하여 앱 내부 이동을 처리합니다.

---

## 10. Deep Link 처리

푸시 클릭 시 앱은 Deep Link를 통해 특정 화면으로 이동합니다.

### 예시

```
myapp://announcement/123
```

### 처리 흐름

```
Push 클릭
    ↓
앱 실행
    ↓
Deep Link 파싱
    ↓
해당 화면 이동
```

---

## 11. 로그인 상태 처리

푸시 클릭 시 사용자의 로그인 상태를 확인해야 합니다.

### 처리 흐름

```
Push 클릭
    ↓
앱 실행
    ↓
로그인 상태 확인
    ├─→ 로그인 상태: Deep Link 화면 이동
    └─→ 미로그인 상태: 로그인 화면 이동
                           ↓
                       로그인 성공
                           ↓
                   Deep Link 화면 이동
```

---

## 12. 알림 읽음 처리

푸시 클릭은 읽음 처리 기준이 아닙니다.

읽음 처리는 서버 DB 기준으로 관리합니다.

### 알림 상태

| 상태 | 설명 |
|------|------|
| `read = false` | 읽지 않음 |
| `read = true` | 읽음 |

### 읽음 처리 방식

대표적으로 두 가지 방식이 있습니다.

#### 방식 1: 알림센터 진입 시 전체 읽음 처리

사용자가 알림센터에 진입하면 모든 알림을 읽음 상태로 변경합니다.

#### 방식 2: 알림 클릭 시 개별 읽음 처리

사용자가 특정 알림을 클릭할 때마다 해당 알림만 읽음 상태로 변경합니다.

---

## 결론

본 푸시 시스템은 다음 핵심 원칙을 기반으로 설계되었습니다.

- **Push와 Notification 시스템 분리**
- **Hybrid Push 전략 (Topic + Device Token)**
- **Queue 기반 확장 구조**
- **Deep Link 기반 화면 이동**
- **서버 DB 기반 알림 관리**

이 구조는 초기 서비스 운영뿐 아니라 사용자 증가 시에도 안정적으로 확장 가능한 아키텍처를 제공합니다.
